# 会话归档

把一次对话、迭代、阅读上下文或跑偏讨论压缩成未来 agent 能直接相信的项目记忆。

归档分三步：先判断内容类型，再写入项目最稳定的位置，最后只给用户一份短摘要。

## 入口与依据

判定依据全部写在 [归档规范](references/archive-spec.md)。该文件分五大节：

1. **五原则** —— 只存事实 / 不做分析、按内容分流、用户未确认不写、推断与未验证必须分标签。
2. **五维度** —— 写入前自检：触发 / 位置 / 区分 / 入口 / 收尾。
3. **五心理学** —— 失败模式的认知机制：完整性幻觉 / 复盘冲动 / 推测变事实 / 焦虑储存 / 重写历史。
4. **对话严苛规则** —— 收尾回复 ≤ 12 行、固定结构、禁止展开新方案。
5. **语言纯化规则** —— 中文段落不夹裸英文、英文模板保持纯英文、文件名命令名保留原文。

写归档前必须读取该规范，禁止自由发挥格式。

## 触发规范

### 显式触发

用户说这些词时立刻归档：

- 归档、收尾、先到这、停一下、保存上下文
- 跑偏了、太散了、先看反馈
- handoff、交接、给下一个 agent 看
- 总结一下这轮、保留上下文

### 自检触发

用户不一定知道该归档。出现以下信号时必须主动建议（仍需用户确认）：

- 对话已跨多个主题，但没有统一记录。
- 已经做完一轮功能、修复、测试、阅读或决策。
- 聊天里出现多个文件路径、命令、结论、风险，后续容易丢。
- 用户开始说「等等 / 先停 / 有点乱 / 回到刚才」。
- 即将切换任务、切换 agent、结束当天工作或进入长上下文。
- 你发现自己需要反复回忆前文才能继续。

建议句式：

```text
这轮上下文已经有点长，而且有几个结论和文件路径值得留住。先归档成一份短记录，再继续。
```

只有用户确认或显式要求归档时才写文件。

## 归档位置

不要假设项目一定有某套文档结构。按优先级选位置：

1. **已有约定优先** —— 项目已有日志、对话纪要、决策记录、handoff、QA 输出或 docs 索引时，沿用其命名与目录。
2. **按内容分流** —— 讨论归讨论、迭代归迭代、交接归交接、QA 归 QA。禁止塞万能文件。
3. **没有约定才新建** —— 在 `docs/` 下创建最小结构，例如 `docs/session-archive.md` 或 `docs/archives/YYYY-MM-DD-[topic].md`。
4. **长期事实进长期文档** —— 影响路线、接口、决策或后续工作的内容才进 roadmap / architecture / decision 文档。
5. **临时材料留索引** —— handoff、QA findings、长输出、截图说明等单独成文件，但要在最近的日志或索引里留路径和用途。

推荐路由：

| 内容性质 | 推荐归档方式 |
| --- | --- |
| 产品 / 架构 / UX 讨论 | 按日期和主题命名的对话纪要 |
| 功能 / 修复 / 样式 / 测试迭代 | 当日工作日志或迭代记录 |
| 阅读文档 / 源码 / PR 后的上下文 | 阅读纪要或会话归档，保留读过的路径 |
| QA findings / 验收问题 | 问题清单文件，并在日志中索引 |
| 给下一个 agent 的交接 | 短 handoff 文件，包含入口、禁改项、验收标准 |
| 没有 docs 的项目 | 新建一个最小会话归档文件，禁止搭复杂文档系统 |

## 收尾回复

归档完成后，回复 ≤ 12 行，固定结构：

```text
已归档。

文件：
- ……

本次保留：
- ……

下一轮先看：
- ……
```

禁止在收尾回复里展开新方案。
