# 写一个自己的 skill —— 采访式生成

> 说白了,**大多数人不是写不出 skill,是不知道一个"好用"的 skill 长什么样**。
>
> 这个 skill 不教你 markdown 语法,它**采访你**。问完 6 件事,SKILL.md 自动出来,直接能用。

---

## 为什么有这个 skill

你脑子里有一套自己反复用的工作流 —— 代码评审的固定问法、产品讨论的固定框架、写文档的固定结构 —— 你想把它做成 skill 让 Claude 自动遵守,但落笔时永远卡在:

- 这个 skill 在什么时候该被触发?
- 反模式怎么写才不空洞?
- 输出该长什么样?
- description 字段到底写多详细?

纠结到放弃,然后继续手动每次重复。

**根本问题**:写 skill 这件事本身,就需要一个 skill。这就是它。

---

## 设计哲学:吃自己的狗粮

本 skill **严格遵守 `focused-discussion` 的对话纪律**:

- **一次只问一个问题** —— 不甩 ABCD 选项,不丢问题清单
- **答完一题再开下一题** —— 用户没回答前,不预设下一个问题
- **不替用户脑补** —— 用户没说的东西不替他补全,不清楚就追问

如果违反这一点,你写出来的 skill 不是"用户的 skill",是"你脑补的 skill"。**脑补出来的 skill 没人会用,包括用户自己**。

> **`focused-discussion` 是本 skill 的前置依赖**,同仓库一起发布。安装本 skill 时请一起安装它。

---

## 反模式(❌ 不要这样做)

### 1. 上来就丢模板让用户填

"请按以下字段填写:name / description / trigger / anti-pattern / output ……"

→ 用户看到一堆字段直接关闭窗口。**采访式 ≠ 表单式**,二者的区别是:表单是"我列好问题你填",采访是"我顺着你的话往下问"。

### 2. 一次问 5 个问题

"请告诉我:这个 skill 解决什么问题、什么时候触发、反模式是什么、正确做法是什么、输出长什么样?"

→ 用户脑容量爆炸,放弃回答。**单线追问,一个一个来,前一个没闭合不开下一个**。

### 3. 用户答得糙就放过

用户答"差不多就是 XX 的时候" → 你也就"差不多"写一下 → 写出来的 skill 触发不准、规则模糊、Claude 根本不会用。

**追到具体**:让用户举一个真实失败案例,不接受"抽象描述"和"差不多"。

### 4. 不验证就生成

用户答了 6 个问题,你立刻 Write SKILL.md。

→ **生成前必须回放**:"我听到的是 X、Y、Z,对吗?"——不对就改,对了再写。回放这一步**不能省**,因为采访过程里你大概率有 1-2 处误读。

### 5. 生成完不告诉用户怎么用

写完 SKILL.md 就结束 → 用户不知道接下来要做什么、要不要重启 Claude、CLAUDE.md 要不要改。

→ **最后必须给一个"如何启用"的 3 行清单**。

---

## 采访流程(✅ 标准 6 问,严格按顺序)

**严格按顺序一题一答**,用户没答清楚就追问,不要跳。

### 第一问:触发场景

> 「这个 skill,你希望 Claude 在**什么时候**自动用上?给我一个具体的例子,不要描述。」

**追问示例**:
- 用户答"代码评审时" → 追问"哪种?PR 评审?自我评审?新人代码评审?"
- 用户答"写文档时" → 追问"哪种文档?README?变更日志?设计文档?"
- 用户答"开会时" → 追问"开什么会?需求评审?事故复盘?周会?"

**不接受**"差不多就是 XX 的时候"。追到能说出具体场景为止。

### 第二问:真实失败案例

> 「上一次你**没用这个 skill 的时候**,具体出了什么问题?越具体越好,能复述一句对话最好。」

**为什么这样问**:好 skill 都来自真实的痛。用户答不出来失败案例 → 说明这个 skill 还没到该写的时候,**这件事一周可能就发生 1 次,做成 skill 不划算**。

如果用户答"嗯……一时想不起来" → 直接说:"那这个 skill 先别做,等下次真的栽跟头了再回来。"

### 第三问:反模式

> 「在这个场景里,Claude 通常会做错什么?列 2-3 个**具体行为**,不要抽象。」

**追问示例**:
- 用户答"Claude 会跑偏" → 追问"怎么跑偏?是改了不该改的文件,还是开始聊别的话题,还是给一堆备选方案?"
- 用户答"Claude 太啰嗦" → 追问"啰嗦在哪?重复确认?加废话注释?写太长的总结?"

### 第四问:正确做法

> 「那你希望 Claude **具体怎么做**?给我 2-3 条规则。」

如果用户答得抽象(比如"简洁一点") → 追问"具体怎么算简洁?字数限制?不写注释?只输出 diff?"

### 第五问:输出格式

> 「用完这个 skill 之后,你希望最终拿到什么?一段对话?一个文件?一份清单?一段 diff?」

如果是文件 → 让用户描述文件长什么样,或者给一个现成的例子。

### 第六问:命名

> 「斜杠命令叫什么?中英文都行,我帮你转 kebab-case。」

如果用户没主意 → 根据前 5 问内容**主动给一个推荐名**,让用户 yes/no。**不要列 3 个让用户选**(那就违反了 focused-discussion)。

---

## 生成前必须回放

6 问答完,**不要立刻写 SKILL.md**。先回放:

```
我听到的是:

- 触发:[xxx]
- 失败案例:[xxx]
- 反模式:[xxx 1] / [xxx 2] / [xxx 3]
- 正确做法:[xxx 1] / [xxx 2] / [xxx 3]
- 输出:[xxx]
- 名称:[xxx]

对吗?有要改的地方吗?
```

用户确认 → 才生成。

## 文件落位

生成的 SKILL.md 放在:

```
.claude/skills/{{slug}}/SKILL.md
```

**不要** 放到项目根目录、**不要** 自作主张建多层子目录、**不要** 拆成多个文件。**一个 skill 一个 SKILL.md,够了**。复杂逻辑写在 SKILL.md 内部章节里,不要分文件。

---

## 启用清单(生成后必须告诉用户)

写完 SKILL.md,**最后输出这 3 行给用户**:

```
✅ skill 已生成:.claude/skills/{{slug}}/SKILL.md

启用方式:
1. 在本会话直接输入 /{{slug}} 就能用(无需重启)
2. 项目里其他人拉代码后也自动可用(已在 .claude/skills/,跟仓库走)
3. 用 2-3 次之后觉得哪里不顺手 → 直接改 SKILL.md,改完立刻生效
```

---

## 落地建议

- **从你最重复的工作流开始** —— 一周做 5 次以上的事,值得做成 skill。一次性的别做。
- **别一次写 5 个 skill** —— 写一个,用一周,根据真实使用反馈再迭代。**没用过的 skill 永远是错的**。
- **skill 数量超过 3 个时,在 CLAUDE.md 里建一张表索引** —— 不然 Claude 自己找不到该用哪个,等于白写。
- **写完 skill 别藏着** —— 团队成员都能受益(前提是不搞古法编程)。
