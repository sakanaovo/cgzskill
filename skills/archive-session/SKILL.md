# 会话归档

把一次对话、开发迭代、阅读上下文或跑偏讨论压缩成未来 agent 能直接相信的项目记忆。

归档流程分三步:先判断内容类型,再写入项目里最稳定的位置,最后只给用户一个短摘要。

## 核心原则

- 归档只保存事实、结论、路径、验证结果和下一步;不重新评估、不新增方案、不补工时优先级。
- 优先更新项目已有 docs,不要另起一套文档系统。
- 用户说“先到这 / 跑偏了 / 归档”时,停止扩展讨论,先把当前上下文收住。
- 如果用户没有意识到该归档,但上下文已经明显变长或分支变多,先建议归档并说明理由;不要擅自写文件。
- 不记录 token、cookie、私钥、个人隐私、登录态截图等敏感信息。
- 不修改业务代码,除非用户明确要求同时修代码。

## 触发规范

### 显式触发

用户说这些词时直接归档:

- 归档、收尾、先到这、停一下、保存上下文
- 跑偏了、太散了、先看反馈
- handoff、交接、给下一个 agent 看
- 总结一下这轮、保留上下文

### 自检触发

用户不一定知道该归档。出现以下信号时,主动建议归档:

- 对话已经跨过多个主题,但没有一个统一记录。
- 已经做完一轮功能、修复、测试、阅读或决策。
- 聊天里出现多个文件路径、命令、结论、风险,后续容易丢。
- 用户开始说“等等”“先停”“有点乱”“回到刚才”。
- 即将切换任务、切换 agent、结束当天工作或进入长时间上下文。
- 你发现自己需要反复回忆前文才能继续。

建议句式:

```text
这轮上下文已经有点长,而且有几个结论和文件路径值得留住。要不要我先归档成一份短记录,再继续?
```

只有用户确认,或用户已经明确要求归档时,才写文件。

## 归档位置规范

不要假设项目一定有某套文档结构。先看项目已有约定,再选择最贴近的归档位置:

1. **已有约定优先**:如果项目已经有日志、对话纪要、决策记录、handoff、QA 输出或 docs 索引,沿用它的命名和目录。
2. **按内容分流**:讨论归讨论,迭代归迭代,交接归交接,测试发现归测试发现。不要把所有内容塞进一个万能文件。
3. **没有约定时才新建**:没有合适位置时,在 `docs/` 下创建最小结构,例如 `docs/session-archive.md` 或 `docs/archives/YYYY-MM-DD-[topic].md`。
4. **长期事实进长期文档**:只有影响路线、接口、决策或后续工作的内容,才写进 roadmap/architecture/decision 类文档。
5. **临时材料留索引**:handoff、QA findings、长输出、截图说明等可以单独成文件,但要在最近的日志或索引里留路径和用途。

推荐路由:

| 内容性质 | 推荐归档方式 |
| --- | --- |
| 产品/架构/UX 讨论 | 一篇按日期和主题命名的对话纪要 |
| 功能/修复/样式/测试迭代 | 当日工作日志或迭代记录 |
| 阅读文档/源码/PR 后的上下文 | 阅读纪要或会话归档,保留读过的路径 |
| QA findings / 验收问题 | 问题清单文件,并在日志中索引 |
| 给下一个 agent 的交接 | 短 handoff 文件,包含入口、禁改项、验收标准 |
| 没有 docs 的项目 | 新建一个最小会话归档文件,不要搭复杂文档系统 |

## 写入规范

写归档前先读取 [归档规范](references/archive-spec.md)。它定义:

- 一份合格归档必须包含什么
- 如何区分事实、推断和未验证内容
- 什么时候新建文件、什么时候追加
- 讨论归档、迭代归档、handoff 的推荐模板
- 索引应该记录什么

不要在没有读取规范的情况下自由发挥归档格式。

## 收尾回复

归档完成后,回复不超过 12 行:

```text
已归档。

文件:
- ...

本次保留:
- ...

下一轮先看:
- ...
```

不要在收尾回复里再展开新方案。
