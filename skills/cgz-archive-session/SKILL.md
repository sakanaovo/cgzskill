# 会话归档

把一次对话、迭代、阅读上下文或跑偏讨论压缩成未来 agent 能直接相信的项目记忆。

归档分三步：先判断内容类型，再写入项目最稳定的位置，最后只给用户一份短摘要。

## 入口与依据

判定依据全部写在 [归档规范](references/archive-spec.md)。该文件分五大节：

1. **五原则** —— 只存事实 / 不做分析、按内容分流、用户未确认不写、推断与未验证必须分标签。
2. **五维度** —— 写入前自检：触发 / 位置 / 区分 / 入口 / 收尾。
3. **五心理学** —— 失败模式的认知机制：完整性幻觉 / 复盘冲动 / 推测变事实 / 焦虑储存 / 重写历史。
4. **对话严苛规则** —— 收尾回复 ≤ 12 行、固定结构、禁止展开新方案。
5. **语言纯化规则** —— 按选择的文档语言输出，代码、schema、路径和来源原文保留。

写归档前必须读取该规范，禁止自由发挥格式。

## 文档语言

本人的新文档按“本次明确请求 → 已存 `document_language` → 项目语言约定 → 首次询问”选择语言；首次确认后保存，单次要求不修改长期设置。缺字段只补语言，保留本地作者身份。共享文件遵循项目的 `project_document_language` 或已有约定，个人偏好不覆盖团队语言。正文可翻译，schema、路径、ID 和来源引用不翻译；不改写不可变历史。完整规则见本 skill 的 references。

## 触发规范

### 显式触发

用户说这些词时立刻归档：

- 归档、收尾、先到这、停一下、保存上下文
- 跑偏了、太散了、先看反馈
- handoff、交接、给下一个 agent 看
- 总结一下这轮、保留上下文

### 自检触发

用户不一定知道该归档。出现以下信号时必须主动建议（仍需用户确认）：

- 对话已跨多个主题，但没有统一记录。
- 已经做完一轮功能、修复、测试、阅读或决策。
- 聊天里出现多个文件路径、命令、结论、风险，后续容易丢。
- 用户开始说「等等 / 先停 / 有点乱 / 回到刚才」。
- 即将切换任务、切换 agent、结束当天工作或进入长上下文。
- 你发现自己需要反复回忆前文才能继续。

建议句式：

```text
这轮上下文已经有点长，而且有几个结论和文件路径值得留住。先归档成一份短记录，再继续。
```

只有用户确认或显式要求归档时才写文件。

## 归档位置

每次写独立记录，默认 `docs/archives/YYYY-MM-DD-<record_id>.md`，`record_id` 为随机 UUID；不用日期、作者名或分支名保证唯一。先按本 skill 的归档规范读取本地作者身份；未初始化时也可在确认身份后按最小协议使用。

已有项目目录、索引或单文件只读兼容，不迁移历史。新记录沿用已确认的独立目录；旧约定只有共享单文件时，先确认改用独立目录，禁止继续追加共享热点。

每条记录含作者 ID / 别名、日期与时区、范围、验证状态、可获取的分支 / 基线 commit；更正写新记录并引用旧 ID。原始记录不可改写或去重删除，不自动追加共享索引、`AGENTS.md` 或 `docs/ai-lessons.md`。

新教训写独立 `docs/lessons/YYYY-MM-DD-<record_id>.md`。汇总只合并同义且同范围的内容并保留来源；互补差异保留，矛盾标 `pending` 待确认，不自动采纳为规则。

## 收尾回复

归档完成后，回复 ≤ 12 行，固定结构：

```text
已归档。

文件：
- ……

本次保留：
- ……

下一轮先看：
- ……
```

禁止在收尾回复里展开新方案。
