# 归档规范

一份合格归档必须让未来 agent 在 3 分钟内恢复上下文,但不会被旧聊天噪声带偏。

## 必须包含

- **标题**:日期 + 主题,主题用用户目标命名,不要用“杂项/总结/聊天记录”。
- **触发原因**:为什么归档,例如收尾、跑偏、handoff、完成一轮迭代、长上下文压缩。
- **当前目标**:用户真正要完成什么,用 1-2 句写清楚。
- **已确认事实**:只写已经读到、验证过、用户确认过或代码实际存在的内容。
- **关键路径**:文件、链接、命令、测试输出、截图或素材位置。
- **决策记录**:写“决定是什么 + 为什么”,不展开备选方案历史。
- **未决问题**:后续还需要确认什么,每条都能被行动。
- **下一步入口**:未来 agent 应该先读什么、先跑什么、先问什么。

## 必须区分

用明确标签分开:

```markdown
## 已确认

## 推断

## 未验证

## 下一步
```

不要把推断写成事实。不要把“可能有用”的想法写成待办。

## 粒度

- 一条归档记录只服务一个主题或一轮迭代。
- 多主题混在一起时,先拆主题;不能拆时,在文档内用清晰小节隔开。
- 每条 bullet 尽量能独立被执行或验证。
- 原文只保留必要短摘录;长材料用路径、链接或附件索引。

## 语言

- 用短句、事实句、命令式下一步。
- 不写心理活动、过程复盘、客套话。
- 不写“我认为很重要”这类无证据判断。
- 不用大段表格制造阅读负担;表格只用于路径索引、测试结果、决策记录。

## 更新还是新建

- 同一主题当天继续推进:优先追加到已有归档。
- 新主题、新结论组或新交接对象:新建归档。
- 长期文档只接收稳定结论;临时讨论留在会话归档。
- 修改已有归档时,追加新小节或补充状态,不要重写历史让旧结论失踪。

## 内容压缩

只保留 durable facts:

- 用户最初目标
- 已确认的结论和决策
- 修改过或阅读过的文件路径
- 关键命令、测试结果、失败样例
- 仍然未知或未验证的风险
- 下一轮 agent 应该先读哪里、先做什么

删除这些内容:

- 重复确认、闲聊、语气修饰
- 已被推翻的猜测,除非它解释了为什么改方向
- 未被用户要求的新方案、工时、优先级
- 大段原文复制。需要保留原文时,用路径或短摘录索引。

## 讨论归档模板

```markdown
# 对话归档 · YYYY-MM-DD

**主题**: [一句话]
**触发原因**: [归档 / 跑偏 / 收尾 / handoff]

## 当前焦点

[本轮真正要解决的问题]

## 已确认

- ...

## 推断

- ...

## 未验证

- ...

## 下一步

- Read first: `path`
- Next: ...
```

## 迭代归档模板

```markdown
## YYYY-MM-DD HH:mm - [本轮迭代名称]

Goal:
- ...

Changed:
- `path`: ...

Verified:
- `command`: result

Decisions:
- ...

Risks:
- ...

Next:
- ...
```

## Handoff 模板

```markdown
# Handoff · YYYY-MM-DD

Read first:
- `path`

Do not change:
- ...

Current state:
- ...

Bug / task:
- ...

Acceptance:
- ...

Run:
- `command`
```

## 索引规范

如果创建了新归档文件,同步更新最接近的索引。没有索引时,可以在同目录创建一个最小索引。

索引只记录:

- 日期
- 主题
- 文件路径
- 1 句摘要
- 必要的下一步

不要删除历史记录。不要为了索引复制全文。
